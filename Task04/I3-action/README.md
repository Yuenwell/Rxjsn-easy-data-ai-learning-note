# I3 课后行动 · 产品评论智能加工

[返回 Task04 学习笔记](../README.md)

**实测日期** 2026-11-25  
**环境** 本机 seekdb v1.4.0.0，独立实验库

我用 12 条虚构蓝牙耳机评论，回答「这款耳机容易断连吗？主要出现在什么场景？」。实验通过 seekdb 的四个 SQL AI 函数跑通。Embedding 用本机 E5 真实推理，重排和摘要用本地可控的测试端点。重排器和摘要端点的输出用于验证链路、校验和失败处理，延迟和质量数据适用于本次本机实验。

## 1–2. 表结构、逻辑模型和测试数据

| 表 | 主要字段和作用 |
| --- | --- |
| reviews | run_id、review_id、revision、body、embedding、embedding_model。每个运行编号下单独保存评论和向量。 |
| summary_jobs | run_id、scenario、state、attempts、last_error。区分正常运行、429 场景与非法响应场景。attempts 统计完成阶段的 SQL 调用次数。 |
| review_summaries | run_id、summary_key、payload、evidence_revisions、model_version。保存通过校验的正式结果。主键由运行编号和摘要用途组成。 |

脚本通过 DBMS_AI_SERVICE 注册逻辑模型和端点，逻辑名包含运行编号。容器通过本地测试端点调用模型。每次运行使用临时凭据，退出时移除本次注册的模型和端点。

| 逻辑用途 | 类型与 Provider 适配器 | 端点路径 | 实际版本 |
| --- | --- | --- | --- |
| embed | dense_embedding · OPENAI | /embeddings | intfloat/multilingual-e5-small，384 维、INT8 ONNX。 |
| rerank | rerank · COHERE | /rerank | review-keyword-reranker-v1，按连接故障关键词排序的测试实现。 |
| complete | completion · OPENAI | /chat/completions | review-summary-fixture-v1，模拟返回结构化摘要的测试实现。 |

## 3–6. 向量、召回、重排、生成和校验

1. 对 12 条评论逐条调用 AI_EMBED，文本加上 E5 的 passage 前缀。写入 384 维向量，并记录模型版本。本轮核实 12 条都已写入。
2. 问题加上 query 前缀，单独调用一次 AI_EMBED。Python 暂存查询向量，交给 SQL 用余弦距离取前 6。候选顺序为 **R01 → R03 → R02 → R11 → R09 → R08**。
3. 将 6 条正文一次传给 AI_RERANK。取前 4，得到 **R02 → R01 → R03 → R11**。设备切换的 R02 从第 3 到第 1。
4. AI_PROMPT 拼装模板和四条评论。AI_COMPLETE 调用一次本地测试端点，返回包含 summary、issues、evidence_ids 的 JSON。
5. 程序先解析 JSON，再检查字段类型、摘要长度、场景枚举和证据 ID。每个场景的引用必须来自本次候选，并包含对应场景和连接故障的线索。校验通过才提交正式结果。

下面是本次生成的 JSON。

~~~json
{
  "summary": "候选评论提到连接问题的场景包括地铁、设备切换。",
  "issues": [
    {"scenario": "地铁", "evidence_ids": ["R01"]},
    {"scenario": "设备切换", "evidence_ids": ["R02"]}
  ],
  "evidence_ids": ["R02", "R01", "R03", "R11"]
}
~~~

这里有一个实测局限。**R04 描述隔墙掉线，却没进向量召回的前 6 条**。以三条连接故障评论为目标，这次向量召回命中了其中两条。重排能让 R02 上升，范围仍受候选限制。对问题里的「容易断连吗」，这批虚构评论只支持描述出现过的场景，无法估计真实故障率。

## 7. 请求、延迟和费用

| 阶段 | 实测 HTTP 请求 | 重试 |
| --- | ---: | --- |
| 12 条评论入库 | 12 | 0 |
| 正常查询加工 | 3 | 0 |
| 429 场景 | 4 | 生成端点收到一次重试。应用只执行一次生成 SQL。 |
| 非法响应场景 | 3 | 0 |
| 20 次正常链路测量 | 60 | 0 |
| 合计 | **82** | **1 次 HTTP 重试** |

正常一次加工为 **1 次问题向量化 + 1 次批量重排 + 1 次生成**。AI_PROMPT 不产生 HTTP 调用。

- **查询到校验通过的 P95 为 16.845 ms**。测了 20 次，取排序后第 19 个值。包括 SQL 往返、召回、重排、生成和校验，计时范围到持久化之前。
- 20 次测量中，本地端点自身处理时间的 P95 分别为 Embedding **3.549 ms**、重排 **0.053 ms**、摘要 **0.069 ms**。这些数字与整条链路的 P95 使用不同计时范围。
- **实际模型账单 ¥0**。本地 E5 和两个本地测试端点无外部 API 账单。替换为付费模型后，应使用服务商的计费口径和实际用量，按成功及可能计费的重试请求汇总。

## 8. 故障注入与正式数据检查

| 场景 | 实际观察 | 正式结果 |
| --- | --- | --- |
| 正常响应 | 生成端点返回 HTTP 200，JSON 校验通过。任务状态为 published。 | 写入一条基准摘要。 |
| 一次 HTTP 429 | 同一条 AI_COMPLETE 的端点状态依次是 429、200。本机 seekdb 自行发起第二次 HTTP 请求。任务最后为 already_published。 | 独立连接在两次响应发出前都读到了同一份基准摘要。重试成功后，同一主键仍只有一条，正文与引用版本也一致。 |
| 非法 JSON | HTTP 200 的生成内容为 '{"summary":'，Python 解析抛出 JSONDecodeError。任务状态为 failed。 | 正式表仍只有一条基准摘要，内容和引用版本均一致。 |

429 说明 **一条 SQL 可能对应多次 HTTP 请求**。非法 JSON 说明 **HTTP 200 只证明请求获得了响应**，写入资格由应用的解析和业务校验决定。自动重试是这次安装版本和端点设置下的实测观察。

## 9. 事务边界

| 放置位置 | 具体操作 |
| --- | --- |
| 事务内 · 短 | 一开始写入评论或创建任务状态。生成向量后，批量写入已校验的向量和模型版本。 |
| 事务外 | 调用 AI_EMBED、AI_RERANK、AI_COMPLETE，等待网络、限流和重试。查询向量在本次查询中暂存，候选召回和输出解析也在事务外完成。AI_PROMPT 负责本地组装，本实验将它和生成一起放在事务外。 |
| 事务内 · 短 | 写回前锁定证据行，核对 revision，用唯一键写正式摘要并更新任务状态。失败时另开短事务写失败状态。 |

若模型调用后的校验失败，任务表可以保留失败原因。已发生的模型调用、耗时和可能费用由端点日志记录。正式业务表只接收通过校验、证据版本仍匹配的结果。
